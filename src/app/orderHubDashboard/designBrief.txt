I need to construct a dashboard with important data regarding an application used by store general managers and sales managers to follow through on customer applications and closed deals. Assume the following is or needs to be true
•	The system holds 2 months-worth of data at a time. 
•	Customers apply for leases through three different channels – in-store, web applications, or e-commerce
•	An application can be automatically approved for a certain amount of leasing power or it can be declined
•	Some applications require additional ID verification in-store by the manager before they can be approved
•	Sometime stores create manual applications for customers if the customer can’t apply themselves. In these cases, the automatic approval/denial system is skipped and the manager makes their own determination on whether the customer should be approved for business or not
•	From an application, an agreement order for the customer can be created. A number of steps can be required to move the agreement order to a finalized agreement. Those include calling the customer to welcome them if it’s an ecomm order, checking the customer out if it’s an in-store or web apply order, assigning specific items if the order was creating using placeholder SKUs, or taking an initial payment if the order was marked by the system as requiring one. Sometimes item conflicts can hold an agreement order up. This happens when an item on an order was erroneously assigned to a different one also. This conflicts need to be manually fixed in the system by the manager. There is also a specific type of ecomm order called an express order that needs to be processed quickly because delivery is automatic. If these need item assignments or have item conflicts, those need to be rectified quickly. Sometimes ecomm agreement orders are held up by a third party fraud review help center called the HSC. When this happens, the manager simply needs to wait for them to be resolved. They have no direct control over these, but knowing which are under active HSC review can be helpful.
•	When an agreement order is created from an application, the amount of leasing power associated with the application is decremented by the cost of the lease. The customer can choose to do as many lease agreements as their leasing power will stretch, and the business wants to leave the least amount of remaining leasing power (RLP) on the table as possible
•	“Unconverted” applications are defined as those which have no agreement orders or finalized agreements
•	“Active RLP” is defined as applications with at least one active agreement or agreement order which have leftover RLP
•	The purpose of the dashboard is to help managers understand what’s going on with the applications and agreement orders at a glance. They want to know what’s holding things up, what opportunities there might be to close deals, and how many applications / agreement orders are in each of the various statuses and buckets. They also want to know how much RLP is left to use. Besides that, users need to be better at quickly tackling the tasks that are in their power to move things along. They need to see alerts for priority tasks like welcome calls, correcting conflicts, assigning missing items, checking agreements out, taking initial payments, and verifying identities. This should be basically a blend of alerts and a to-do list prominent near the top of the dashboard
•	There needs to be a obvious organization to the dashboard. There are many ways it could be organized. There are application concerns vs pending agreement concerns. There are alerts/to-do/actionable tasks vs purely analytical data for example
•	Some things that the UX team would like to have is a focus on total numbers of things. For example, number of active agreement orders, number of unconverted applications, number of applications with active RLP, number of declines etc.. They also want a table which shows the five most recent applications with a column for date/time they came in, customer name, and leasing power. They also want a line graph that shows two lines – the top would be total number of applications per each week and the bottom would be total number of converted applications per each week. The aim for 100% conversion would be for those lines to overlap as much as possible
